02 · Fluxo real

Assumir uma tarefa atravessa vários padrões

Nenhum padrão executa tudo. O valor está na colaboração: cada componente responde sua pergunta e o caso de uso preserva a ordem do processo.

Resultado de produto

Um usuário autorizado assume uma tarefa disponível, a movimentação é registrada, a notificação consultiva é publicada e o front recebe um DTO acompanhado da mensagem de sucesso.

01 · Use Case

Recebe a intenção

AssumirTarefaCase mantém visível a sequência completa.

02 · Repository

Carrega o estado

Busca tarefa, usuário atual e responsabilidade de gestão.

03 · Policy

Decide se pode

Bloqueia tarefa ocupada, finalizada ou que exige solicitação.

04 · Mapping

Traduz os dados

Monta movimentação e DTO de saída sem persistir.

05 · Resultado

Fecha o contrato

Entrega sucesso ou falha com mensagens consistentes.

03 · Orquestração

Quem executa e quem encaminha

Use Case e Service podem parecer semelhantes, mas têm compromissos diferentes no AtronRC atual.

Padrão 01 · Use Case

AssumirTarefaCase

Pergunta: qual fluxo executa a intenção “assumir tarefa”?

Coordena usuário atual, tarefa, decisão da policy, persistência, histórico, notificação e saída. Ele conhece a ordem, mas delega os detalhes especializados.

Explique assim

“Um Use Case representa uma intenção completa do usuário ou do sistema e coordena tudo que precisa acontecer para concluí-la.”

Não confunda

Ele não deve virar dono de todas as validações, SQL, mapeamentos e textos de comunicação.

AssumirTarefaCase.csApplication/UseCases/TarefaCases
public async Task<Resultado<TarefaDTO>> ExecutarAsync(int tarefaId)
{
    var usuario = await _usuarioService.ObterUsuarioAtual();
    var tarefa = await _tarefaRepository.ObterTarefaPorId(tarefaId);

    var decisao = _tarefaObtencaoPolicy
        .AvaliarAssuncao(tarefa, possuiGestao);

    if (decisao.TeveFalha)
        return Resultado<TarefaDTO>.Falhas(decisao.Messages);

    // persiste, registra movimentação, notifica e mapeia
}
Padrão 02 · Service / Facade

UsuarioService

Pergunta: qual porta estável atende os consumidores existentes?

Preserva o contrato IUsuarioService e encaminha comandos para casos de uso como criar, atualizar, remover e reativar. Algumas consultas ainda ficam diretamente no serviço, por isso a implementação atual é híbrida.

Explique assim

“A fachada oferece uma entrada conhecida e delega cada intenção ao componente especializado que realmente executa o comportamento.”

Não confunda

Uma fachada não deve voltar a acumular regras novas apenas porque já é conhecida pelos controllers.

UsuarioService.csApplication/Services/EntitiesServices
public async Task<Resultado<UsuarioRequest>> CriarAsync(UsuarioRequest request)
    => await _criarUsuario.ExecutarAsync(request);

public async Task<Resultado> RemoverAsync(string codigo)
    => await _removerUsuario.ExecutarAsync(codigo);

// ObterTodosAsync ainda consulta repositório e mapeia diretamente.
04 · Decisão e seleção

Quatro perguntas parecidas, quatro responsabilidades

Policy, Resolver, Specification e Validation deixam de parecer iguais quando observamos o formato de sua resposta.

Padrão 03 · Policy

TarefaObtencaoPolicy

Pergunta: o usuário pode assumir ou solicitar esta tarefa neste contexto?

Combina estado da tarefa, existência de responsável, exigência de aprovação e responsabilidade de gestão. Retorna Resultado para explicar a recusa.

Explique assim

“Uma Policy toma uma decisão de negócio contextual e informa por que a operação foi aceita ou recusada.”

Não confunda

Policy não escolhe o aprovador e não valida apenas formato de campos.

TarefaObtencaoPolicy.csApplication/Policies/Tarefas
public Resultado AvaliarAssuncao(Tarefa tarefa, bool possuiGestao)
{
    var acesso = ValidarTarefaDisponivel(tarefa, mensagem);
    if (acesso.TeveFalha)
        return acesso;

    return !possuiGestao || tarefa.ExigeAprovacaoParaObter
        ? Resultado.Falha(TarefaResource.Erro_TarefaExigeSolicitacaoObtencao)
        : Resultado.Sucesso();
}
Padrão 04 · Resolver

AprovadorObtencaoTarefaResolver

Pergunta: qual usuário será o aprovador efetivo?

Monta candidatos em ordem, ignora códigos vazios e o próprio solicitante, elimina repetições e retorna o primeiro usuário encontrado.

Explique assim

“Um Resolver recebe várias opções possíveis e devolve uma resposta concreta segundo prioridades e fallbacks conhecidos.”

Não confunda

Ele não decide se a solicitação pode ser criada. Essa decisão pertence à Policy e ao caso de uso.

AprovadorObtencaoTarefaResolver.csApplication/Resolvers/Tarefas
var candidatos = ObterCodigosCandidatos(solicitante, tarefa)
    .Where(codigo => !codigo.IsNullOrEmpty())
    .Distinct();

foreach (var codigo in candidatos)
{
    var aprovador = await _usuarioRepository
        .ObterUsuarioPorCodigoAsync(codigo);

    if (aprovador is not null)
        return aprovador;
}
Padrão 05 · Specification

ModuloExistenteSpecification

Pergunta: este DTO satisfaz o critério de representar o módulo existente?

Recebe um candidato e retorna somente bool. É adequada para critérios reutilizáveis, combináveis ou aplicáveis como filtro.

Explique assim

“Uma Specification é uma pergunta de sim ou não feita sobre um candidato.”

Evidência atual

As classes de Specification existem no Tracker, mas a busca atual não encontrou consumidores. Portanto, o padrão está declarado, mas não há fluxo ativo comprovado neste checkout.

ModuloExistenteSpecification.csApplication/Specifications
public bool IsSatisfiedBy(ModuloDTO dto)
{
    return _moduloExistente is not null
        && _moduloExistente.Codigo == dto.Codigo.ToUpper();
}
Padrão 06 · Validation

TarefaValidador

Pergunta: os dados enviados possuem formato e coerência suficientes?

Valida obrigatoriedade, tamanhos, período e coerência do destino. Pode acumular várias mensagens antes de devolver a resposta.

Explique assim

“Validation protege a entrada: verifica se os dados chegaram completos e coerentes antes do fluxo continuar.”

Não confunda

Ela não deve decidir autorização contextual nem substituir invariantes obrigatórias da entidade.

TarefaValidador.csApplication/Validador
public IEnumerable<NotificationMessage> Validar(TarefaDTO tarefa)
{
    var notificacoes = new NotificationBag();

    ValidarDestinoInicial(tarefa, notificacoes);
    ValidarConteudo(tarefa, notificacoes);

    return notificacoes.Messages.ToList();
}
05 · Transformação e criação

Mudar forma não é executar o fluxo

Mapeadores, factories, extensions e compositores trabalham sobre dados, mas cada um possui um resultado diferente.

Padrão 07 · Mapping

TarefaMovimentacaoMapping

Pergunta: como representar uma movimentação no contrato esperado?

Transforma entidades em DTOs, DTOs em entidades e monta representações específicas para criação, atualização e obtenção.

Explique assim

“Mapping traduz dados entre formatos sem decidir se a operação pode acontecer e sem persistir.”

Não confunda

Mapeamento não é validação, repositório ou caso de uso.

TarefaMovimentacaoMapping.csApplication/Mapping
public TarefaMovimentacaoDTO MapearParaCriacao(
    Tarefa tarefa,
    Usuario responsavel)
{
    return new TarefaMovimentacaoDTO
    {
        Id = tarefa.Id,
        ResponsavelCodigo = responsavel.Codigo,
        TipoMovimentacaoTarefa = TipoMovimentacaoTarefa.Criacao
    };
}
Padrão 08 · Factory

TokenFactory e CriarPendente

Pergunta: como construir corretamente um novo objeto complexo?

TokenFactory monta token, refresh token e DTOs relacionados. No domínio, SolicitacaoObtencaoTarefa.CriarPendente centraliza o nascimento de uma solicitação pendente.

Explique assim

“Uma Factory concentra a criação quando montar o objeto corretamente exige regras, dependências ou várias etapas.”

Não confunda

Factory cria. Ela não é responsável pelo ciclo completo de uso, persistência e notificação do objeto.

SolicitacaoObtencaoTarefa.csDomain/Entities
public static SolicitacaoObtencaoTarefa CriarPendente(
    Tarefa tarefa,
    Usuario solicitante,
    Usuario aprovador)
{
    return new SolicitacaoObtencaoTarefa
    {
        TarefaId = tarefa.Id,
        SolicitanteId = solicitante.Id,
        AprovadorId = aprovador.Id,
        Status = StatusSolicitacaoObtencaoTarefa.Pendente
    };
}
Padrão 09 · Extension

TarefaVinculoExtensions

Pergunta: qual operação pequena e reutilizável merece uma chamada legível?

Centraliza a atualização coerente de navegação, ID e código ao vincular departamento, cargo ou usuário.

Explique assim

“Uma Extension dá nome a uma operação pequena sobre um tipo existente sem criar herança nem inflar a classe original.”

Não confunda

Se a operação consulta banco, coordena etapas ou possui dependências, ela deixou de ser uma extension simples.

TarefaVinculoExtensions.csDomain/Extensions
public static void VincularDepartamento(
    this Tarefa tarefa,
    Departamento departamento)
{
    tarefa.Departamento = departamento;
    tarefa.DepartamentoId = departamento.Id;
    tarefa.DepartamentoCodigo = departamento.Codigo;
}
Padrão 10 · Compositor

TarefaEmailCompositor

Pergunta: como montar a comunicação final de atribuição?

Escolhe resource, template, assunto, modelo e destinatário. O renderer transforma essa composição em EmailRequest.

Explique assim

“O Compositor reúne conteúdo e contexto para produzir uma mensagem pronta; outro componente cuida do transporte.”

Não confunda

Compor e enviar são responsabilidades separadas. O compositor não deve conhecer SMTP ou Brevo.

TarefaEmailCompositor.csApplication/Email/Compositores
var template = new EmailTemplateDefinition(
    typeof(TarefaEmailCompositor).Assembly,
    TemplateResourceName,
    assunto,
    TarefaResource.Titulo_EmailTarefaAtribuida);

return _renderer.Renderizar(
    template,
    model,
    [usuario.Email]);
06 · Fronteiras

Dados, configuração e grupos de dependências

Esses componentes ligam o fluxo a recursos externos ou organizam acesso a colaboradores, sem assumir a regra completa do produto.

Padrão 11 · Repository

ITarefaRepository / TarefaRepository

Pergunta: como consultar e persistir tarefas?

O contrato fica no domínio e a implementação com EF Core fica na Infrastructure. O repositório conhece consultas, carregamentos e persistência, mas não decide sozinho o caso de uso.

Explique assim

“Repository é a fronteira de persistência: oferece operações no vocabulário do domínio e esconde o mecanismo de banco.”

Não confunda

Uma consulta pode proteger concorrência e consistência técnica, mas a política contextual continua fora do repositório.

TarefaRepository.csInfrastructure/Repositories
public async Task<Tarefa> ObterTarefaPorId(int id)
{
    return await _context.Tarefas
        .Include(tarefa => tarefa.EstadoDaTarefa)
        .Include(tarefa => tarefa.Usuario)
        .Include(tarefa => tarefa.Departamento)
        .Include(tarefa => tarefa.Cargo)
        .FirstOrDefaultAsync(tarefa => tarefa.Id == id);
}
Padrão 12 · Provider

ResponsavelNotificacaoEstoqueProvider

Pergunta: qual valor configurado deve ser disponibilizado ao consumidor?

Recebe o código configurado pela composição do módulo e o entrega ao serviço de notificação do Stock. Não escolhe entre vários responsáveis.

Explique assim

“Provider fornece um valor ou recurso vindo de configuração ou integração; ele não aplica uma prioridade de negócio entre candidatos.”

Não confunda

Se no futuro houver várias fontes ordenadas de responsável, a seleção poderá justificar um Resolver próprio.

ResponsavelNotificacaoEstoqueProvider.csApplication/Providers/Notificacoes
public sealed class ResponsavelNotificacaoEstoqueProvider(
    string codigoResponsavel)
{
    public string ObterCodigoResponsavel()
        => codigoResponsavel ?? string.Empty;
}
Padrão 13 · Context

UsuarioContext

Pergunta: quais colaboradores formam o contexto compartilhado de usuário?

Agrupa serviço, repositório, cache e dados complementares usados por fluxos de autenticação. É uma solução localizada, não a forma padrão de injetar qualquer dependência.

Explique assim

“Context reúne dependências que pertencem a um mesmo recorte operacional para transportá-las juntas.”

Cuidado

Se começar a expor serviços sem coesão ou esconder dependências reais, transforma-se em service locator e dificulta entender o fluxo.

UsuarioContext.csApplication/Services/Contexts
public class UsuarioContext : IUsuarioContext
{
    public IUsuarioService UsuarioService { get; }
    public IUsuarioRepository UsuarioRepository { get; }
    public ICacheUsuarioService CacheUsuarioService { get; }
    public IDadosComplementaresDoUsuarioService DadosComplementaresDoUsuarioService { get; }
}
07 · Contrato transversal

Resultado<T> faz o fluxo falar a mesma língua

O contrato reúne payload, sucesso, falha e mensagens. Casos de uso e serviços conseguem propagar uma falha sem criar um novo canal de erro em cada camada.

Padrão 14 · Result

Resultado<T>

Pergunta: como devolver dados e mensagens de uma operação de forma uniforme?

Herda de NotificationBag, carrega o payload em Dados e deriva sucesso ou falha das mensagens de erro.

Explique assim

“Resultado é o envelope da operação: leva os dados quando dá certo e explica o problema quando dá errado.”

Não confunda

Ele transporta o resultado. Não deve virar o lugar onde as regras do caso de uso são executadas.

Resultado.csFramework/Shared/Domain/ValueObjects
public class Resultado<T> : Resultado
{
    public new T? Dados { get; private set; }

    public static Resultado<T> Sucesso(T data)
        => new(true, data);

    public static Resultado<T> Falha(string mensagem)
    {
        var resultado = new Resultado<T>(false);
        resultado.AdicionarErro(mensagem);
        return resultado;
    }
}
08 · Decisão prática

Como escolher sem decorar nomes

Comece pela pergunta e pelo tipo de resposta esperado. O sufixo vem depois da responsabilidade.

“Pode executar?”

Policy

Use quando a resposta depende de ator, operação, estado ou consultas e precisa explicar a recusa.

“Qual deles?”

Resolver

Use quando há candidatos ou fontes ordenadas e apenas um resultado deve prevalecer.

“Satisfaz?”

Specification

Use para um predicado reutilizável sobre um candidato, normalmente retornando bool.

“Está coerente?”

Validation

Use para campos, formatos, limites e coerência da entrada, com possibilidade de acumular mensagens.

“Como representar?”

Mapping

Use para converter entidade, DTO, request, response ou outra forma de transporte.

“Como criar?”

Factory

Use quando a construção correta do objeto concentra regras ou etapas relevantes.

“Como fornecer?”

Provider

Use para disponibilizar configuração ou recurso externo sem prioridade contextual de negócio.

“Como persistir?”

Repository

Use como fronteira para consultas e gravações no vocabulário do domínio.

“Qual fluxo?”

Use Case

Use para coordenar a intenção completa, reagindo aos resultados dos demais colaboradores.

09 · Comunicação

Um roteiro para explicar qualquer padrão

A explicação fica mais clara quando parte do problema de produto, passa pelo contrato e termina no limite da responsabilidade.

01

Comece pelo problema

“Quando alguém tenta assumir uma tarefa, o sistema precisa verificar se ela está disponível e se o usuário pode agir diretamente.”

02

Formule a pergunta

“Quem responde se a operação pode acontecer?” A resposta aponta para a Policy.

03

Mostre a entrada e a saída

A Policy recebe tarefa e contexto de gestão; devolve sucesso ou uma mensagem de recusa.

04

Mostre o consumidor

O Use Case chama a Policy e encerra o fluxo quando recebe uma falha.

05

Defina o limite

A Policy não persiste, não envia notificação e não escolhe aprovador.

06

Compare com o vizinho

Policy decide “pode?”. Resolver responde “qual?”. Validation pergunta “os dados estão coerentes?”.

Resumo de bolso

Responsabilidade primeiro, sufixo depois.

No AtronRC, o Use Case coordena, a Policy decide, o Resolver escolhe, a Specification testa, a Validation confere, o Mapping traduz, a Factory cria, a Extension nomeia uma operação pequena, o Repository persiste, o Provider fornece, o Compositor monta e o Resultado transporta a resposta.
